打开 [raster.adcakeyuan.top](https://raster.adcakeyuan.top)，你会看到一个贴图立方体、一颗 Phong 球和一张环面在转。没有 WebGL，没有 WebGPU，没有三方渲染库——每一颗像素都是 TypeScript 在 `Uint8ClampedArray` 上算出来的。仓库在 [huqinyuan923-hue/rasterizer](https://github.com/huqinyuan923-hue/rasterizer)，运行时零 npm 依赖。

做这件事不是为了性能（打不过任何 GPU），而是为了把渲染管线的每一步都放在手上：深度怎么判平局、重心坐标怎么插值、裁剪裁掉一半三角形之后属性跟着谁走。这些在 GPU 上是被固定功能管线吞掉的细节，手写一遍才知道每一条都是设计决策。

## 黄金图先行：把「看起来对」变成逐位相等

项目的第一天没有写任何光栅化代码，写的是验证基建：一个 PPM(P6) 的编解码器和一个逐像素 diff 工具。

PPM 是最朴素的图像格式——文件头之后就是裸的 RGB 字节流，十几行就能手写编解码，不需要任何图像库。每张黄金图由一个独立写的参考实现生成，之后 `npm test` 把正式实现的输出和黄金图逐像素比对，容差是 0：

```text
M1: PPM 编解码 + mulberry32 固定种子场景 + 逐像素 diff      13 测试
M2: Bresenham 全象限（双实现 800 条无平局扫描等价）          19 测试
M3: edge-function 填充 + top-left（水密性 600 对扫描）        25 测试
```

两个细节保证了 diff 有意义。第一，场景生成器用固定种子的 mulberry32，禁止无种子随机——黄金图必须可复现。第二，diff 容差取 0 而不是「人眼可接受」，因为渲染误差是会复利的：抗锯齿差半个像素，下一层插值就差更多。容差 0 意味着任何改动要么逐位对，要么明确承认自己改了语义。

后面所有里程碑都遵守同一条纪律：先写参考实现生成黄金图，再写正式实现对拍；测试不过不进下一里程碑，通过即冻结。

## 三角形：edge function 和 top-left 规则

三角形填充的核心是三次点积。对屏幕上的采样点 p 和三条边 v0→v1、v1→v2、v2→v0，分别算边函数，内部点满足全部大于零：

```ts
const E0 = e0x * (py - va.y) - e0y * (px - va.x)
const E1 = e1x * (py - vb.y) - e1y * (px - vb.x)
const E2 = e2x * (py - vc.y) - e2y * (px - vc.x)
if (E0 > 0 && E1 > 0 && E2 > 0) {
  inside = true
} else if (E0 >= 0 && E1 >= 0 && E2 >= 0) {
  inside = (E0 > 0 || tl0) && (E1 > 0 || tl1) && (E2 > 0 || tl2)
} else {
  inside = false
}
```

第二个分支是 top-left 规则：恰好落在边上的采样点（E==0），只当这条边是「top」（水平且朝右）或「left」（朝下）时才算内部。没有这条规则，两个共享一条边的三角形要么都画那个像素（重叠，深度测试下闪烁），要么都不画（露缝）。有了它，反着走的相邻三角形在共享边上恰好「总和且互斥」。测试里专门放了 600 对共享边扫描和一个两三角形接缝特写，就盯这一件事。

另一个容易忽略的约定是采样点位置：像素 (i,j) 的采样点定在 (i+0.5, j+0.5)。定在角上还是中心，决定了哪些边缘像素被划进三角形——它会被写进注释里「冻结」，因为黄金图的一切都建立在这个约定上。

## 深度与透视校正：除法不是可选项

z-buffer 本身不难，难的是平局语义：两个片段深度逐位相等时谁赢？这里钉死为「先画者赢」，测试用二进制精确几何构造了真正的平局场景。同理，深度测试用严格小于——这些约定单看都是武断的，冻结之后它们就变成了「这个渲染器的物理定律」。

真正有内容的是透视校正。屏幕空间里线性插值纹理坐标是错的——错误在大角度平面上表现为纹理「游泳」。正确做法是插值三个量，再相除：

```ts
const denom = lam0 * vaW + lam1 * vbW + lam2 * vcW   // Σλ·(1/w)
const u = (lam0 * vaA[0] + lam1 * vbA[0] + lam2 * vcA[0]) / denom
```

其中每个 varying 都预乘了 `1/w`（即 `u/w`、`v/w`），`denom` 是重心坐标加权的 `1/w` 和。黄金测试里专门构造了掠射角四边形，用解析光线求交在两千多个像素上验证插值结果——纹理「游不游」不需要眼睛判断，逐位 diff 会告诉你。

## 着色与裁剪

着色走了两条路：Gouraud（顶点算好颜色、屏幕空间插值）和 Phong（逐像素算法线和光照）。内联的 Blinn-Phong 和独立实现共享同一组冻结公式，双模式黄金互为仲裁。这一层抓到的 bug 很典型：把屏幕坐标 y 翻转接进管线后忘了同步背面剔除的绕行方向，结果球从内侧看是亮的——黄金图一比对当场现形。

裁剪用 Sutherland–Hodgman 对近平面做多边形裁剪，一个三角形穿出近平面会合法地变成 0、1 或 2 个三角形，每个都带着正确的插值属性继续走管线。在这之前管线里只放了一个「丢弃越远片段」的守卫，M7 把它换成了真裁剪——全部历史黄金图回归通过，是这条纪律最好的广告。

## 冻结语义下的优化还剩多少

管线的注释里写着一句话：「性能优化不得改变求值方式」。除法一律分子分母直除、不用倒数乘法，是为了和参考实现逐位一致——这直接划定了优化的边界：**能改结构，不能改数值结果**。

在这个约束下，两个安全且有效的手法：

```ts
// 行常量提升：py 在整行不变，e_kx*(py - v_k.y) 每行算一次
const ry0 = e0x * (py - vaY)
// 内层每像素只剩
const E0 = ry0 - e0y * (px - vaX)
```

同一操作数、同一运算，只是把每像素一次的乘法挪到每行一次——IEEE 754 下逐位等价。另一个是双线性采样的回绕：`((v % n) + n) % n` 在可证明的定义域内换成单次条件判断，连 NaN 行为都相同。两项合计，演示场景整帧从 50.30ms 降到 48.45ms，Phong 管线吞吐 642k → 658k tris/s。

至于为什么只有 3.7%：核心热路径是每像素四次除法和一组 sqrt，这是冻结语义下透视校正与光照的定价，结构可改的空间都改完了。这个数字本身就是结论——**黄金逐位仲裁会把「聪明」的优化全部拦下，剩下的只有数学上诚实的那些**。
