打开 [cpu.adcakeyuan.top](https://cpu.adcakeyuan.top)，加载的是一个 32094 字的 ROM：它由一台用 TypeScript 逐门仿真出来的 16 位计算机执行，CPU 的每一个时钟沿都由成千上万个 NAND 和 DFF 的真值计算出来。你在页面上按方向键，俄罗斯方块就往下掉——不过这篇文章想讲的不是「能玩」，而是从最原始的门到能玩之间，有哪些东西值得一个一个亲手撞一遍。

整个项目在仓库 [huqinyuan923-hue/nand-computer](https://github.com/huqinyuan923-hue/nand-computer) 里，分硬件、软件两条轨并行推进，最后以跨轨对拍收束。建成之后它是纯静态的：没有后端、没有定时任务、没有用户数据，代码冻结，demo 挂着就行。

## 一份先于代码冻结的契约

两条轨由两个会话同时开工，互相看不见对方的代码。能让它们最后严丝合缝拼起来的，是一份先于一切实现写死的 `SPEC.md`：

```text
- 16 位字、15 位程序地址。A 指令：0 + 15 位值。C 指令：111a cccccc ddd jjj
- 内存映射：RAM 0x0000-0x3FFF；Screen 0x4000-0x5FFF；Keyboard 0x6000
- Screen：512x256 单色；字地址 w=y*32+(x>>4)；像素位=15-(x&15)（MSB=最左像素）
- Keyboard：0=无键；Left=37、Up=38、Right=39、Down=40；keyup 写 0
- 屏幕哈希：8192 个字按大端展开成 16384 字节，取 SHA-256 小写十六进制
```

最后一条最重要。屏幕哈希把「画面长得对不对」变成了一个可以放进断言里的字符串——硬件轨的门级 CPU、硬件轨的行为级参考实现、软件轨的 hackrun 解释器，三套独立代码跑同一个程序，只要哈希逐位相同，谁也没冤枉谁。

这类项目最常见的死法是两层各自「大概对」，拼起来永远差一位。契约冻结之后，任何歧义都归哈希对拍仲裁，而不是归争论。

## 硬件轨：NAND 和 DFF 之外没有现成芯片

门网表引擎是整个硬件轨的地基，核心不到 260 行。芯片不经过 HDL 文本，直接用 TS 组合，然后编译成扁平网表：

```ts
// 求值双后端里最短的一个：JIT 把整张网表拼成一个函数
parts[i] = `w[${gOut[i]}]=(w[${gA[i]}]&w[${gB[i]}])^1;`
```

编译时做三件事：`writer` 数组查多重驱动、连通性校验、Kahn 拓扑排序把门排成无环求值序。解释后端就是按这个顺序逐门执行同一句 NAND；两个后端跑所有黄金测试，谁偏离谁挨抓。

纪律上有一个反直觉的排序：**先写测试向量，再写芯片**。基础门用真值表自动生成黄金；ALU 用 128 组控制位乘操作数对的语义表逐项对拍；CPU 建成之后，写一个约百行的行为级 ISA 解释器当参照物，用 80 个固定种子的随机程序做逐周期 diff——比较的不是一个周期的输出，而是每一步的 A/D/PC/outM/writeM/addressM。错一个周期就当场报周期号，不会带病滚三万周期再爆。

有一个 bug 值得单独记下来：CPU 的 dest 字段位序接反了，`M` 位接到了第 3 位。这种错在单元层面是过的——每一位单独看都像那么回事——只有整机逐周期对拍才会在第一个写内存的 C 指令上炸出来。黄金先行的全部意义，就是让这类错误死在它出生的那一层。

性能上也有一个小的诚实结论。门求值里最内层那句从 `(~(a & b)) & 1` 改成 `(a & b) ^ 1`，0/1 域逐位等价，A/B 实测 JIT 从 50.3 万周期/秒提到 52.5 万——同类改动里能拿到的就是这个量级，再往上就得动结构，而不是动表达式。

## 软件轨：从助记符到方块

软件轨是另一条完全独立的长链：汇编器 → hackrun → VM 翻译器 → Jack 编译器 → OS 子集 → Tetris。验证地基是第二个里程碑里那个 hackrun——因为有了它，后面每一层都不需要等硬件轨，行为断言直接在行为级机器上跑。

Tetris 本体是 400 行 Jack。它的确定性是刻意构造的：

```jack
while (~(gameOver = 1)) {
    let key = Tetris.processInput()
    if (~(key = 40)) {
        let gravCnt = gravCnt + 1
        if (~(gravCnt < SOFT_SUB)) {
            let gravCnt = 0
            do Tetris.gravityStep()
        }
    } else {
        // 按住 Down 时走另一个节奏
    }
    if (~(sceneDirty = 0)) {
        do Tetris.redrawScene()
    }
    do Tetris.busy(SUB_TICKS)
}
```

重力不用系统时间，用 `busy(750)`——一个写死迭代次数的空转循环。这样每一子帧消耗的周期数是常量，键盘输入脚本能以「第几个周期按下哪个键」的精度复现整局游戏，行为级和门级看到的时间线完全相同。运行时校准被明令禁止，因为一旦校准，周期时间线就依赖执行速度，对拍也就失去了意义。

这一轨抓出来的 bug 也最「编译原理」：汇编器把 JLT 和 JGE 的编码写反（行为测试第一个抓到）；编译器给带 `~` 的条件多发 not，导致整批比较逻辑反转；`let a[i] = 含数组读的表达式` 时写地址被 RHS 覆盖，改成先 RHS 后地址；`do` 语句调用完不弹返回槽，每调用泄漏一个栈字——这个最阴险，短测试全绿，游戏玩上几分钟栈就顶穿堆区，分配器开始发疯。

## 一场整机每 435 万周期重启一次的调试夜

Tetris 第一次完整构建出来那天，症状非常诡异：屏幕全黑，但机器没死。把行为级解释器接上探针逐层看，时间线是这样的：

- 开机到进入游戏主循环要 210 万周期，其中清一次屏要 97 万——朴素代码生成器让每个简单循环迭代花约 119 个指令周期，这解释了「慢」，解释不了「黑」。
- 更深的追踪发现，`Screen.clearScreen` 这个只该被调用两次的函数，在 1000 万周期里被调用了 8 次，三个调用方（Screen.init、Output.init、Tetris.run）轮流出现，且每次进入时栈内容逐字节相同。
- 结论：**整机在周期性重启**，周期精确到 4,345,645 个时钟——这不是巧合能造出来的数字，是一条确定性的错误路径在循环。

继续解剖，第一现场在 `Memory.alloc`：一次本不该发生在游戏中的 `String.new` 分配走进了一个已经被写坏的空闲链表，块头写入直接打在了 ARG/THIS/THAT 所在的 RAM 0–15 寄存器区；紧接着某次函数返回时栈指针塌方到 6，最后的 return 以 0 为返回地址跳回引导区——重启。堆被谁写坏的？候选有三个：`do` 调用的栈泄漏顶穿堆区、`String.setInt` 超容量写坏相邻块、`drawRectangle` 对负坐标不裁剪。三个全真，全部在之后的审计轮里修掉了，外加长按自动重复的计数回绕。

这场调试留下的最重要产出不是修复本身，而是那套探针：给解释器加逐函数进入统计、按返回地址反查调用方、监视帧寄存器第一次越界的时刻。**在这类项目里，调试工具是先于功能代码的基建**——探针一晚上的产出，比反复跑「看看这次黑不黑屏」多十倍。

最后一步是把两条轨钉在一起。软件轨交付 `tetris.hack`、26 个键盘事件的输入脚本和 7 个检查点的屏幕哈希；硬件轨把它们填进集成 spec，让门级 CPU 和行为级 oracle 并行逐周期对拍：

```json

"expect": { "checkpoints": { "166446227": "eb9348b8..." } }
```

166,446,228 个周期跑完，零分歧，7/7 哈希一致，终局停在 LINES 1 · SCORE 100。这一行数字的含义是：门级仿真的每一个时钟沿、汇编器生成的每一条指令、编译器吐出的每一段 VM 代码、Jack 写的每一行游戏逻辑，互相之间没有任何一层在「骗」其他的层。
