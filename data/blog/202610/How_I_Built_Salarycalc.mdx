招聘启事上的数字是税前，房东和信用卡只认到手。中间隔着五险一金、个税起征点、专项附加扣除，还有一笔说不清该单独算还是并入综合所得的年终奖。

[SalaryCalc](https://github.com/huqinyuan923-hue/salarycalc) 就是为这笔账写的：一个 HTML 页面、一份 CSS、一个 252 行的 `script.js`，没有构建、没有依赖、没有后端，部署在 GitHub Pages 上。它不替你做申报，只把「钱是怎么被拆开的」摊在桌面上。

## 先定基数，再谈比例

五险一金里最容易被忽略的不是费率，而是**缴费基数**。代码只维护一个 `base`：优先用你填的基数，没填就用月薪；然后用下限往上抬、用上限往下压。

```js
let base = baseIn > 0 ? baseIn : salary
if (bMin > 0) base = Math.max(base, bMin)
if (bMax > 0) base = Math.min(base, bMax)
```

顺序很重要。如果下限填得比上限还大，这段代码不会报错：先抬到下限，再压到上限，最后静默地取上限。现实里这两个值应当由城市和险种决定，工具把它们交给用户，也把校验责任一起交了出去。

比例默认值写在输入框和 `num()` 的兜底里：个人养老 8%、医疗 2%、失业 0.5%，公积金默认 12%；单位养老 16%、医疗 9%、失业 0.5%、工伤 0.4%，公积金与个人同比例。每个数字都能改，但**社保和公积金共用同一个基数**。真实世界里两者的上下限经常不同，这个模型简化掉了那层差异。

```js
const ins = {
  pension: base * rates.pension,
  medical: base * rates.medical,
  unemployment: base * rates.unemployment,
  fund: base * hfRate,
}
const insTotal = ins.pension + ins.medical + ins.unemployment + ins.fund
```

## 个税：年表算，月税取平均

应纳税所得额按年算：年收入减去 6 万元起征点、全年个人五险一金、专项附加扣除乘以 12。然后套 7 档综合所得税率表，最后把年税除以 12，得到页面上展示的「每月个税」。

```js
const annualPre = salary * 12
const taxable = Math.max(0, annualPre - 60000 - insTotal * 12 - extra * 12)
const annualTax = taxOf(taxable, ANNUAL)
const monthlyTax = annualTax / 12
const netMonthly = salary - insTotal - monthlyTax
```

税率表就是标准的综合所得年表：3%、10%、20%、25%、30%、35%、45%，速算扣除数从 0 到 181920。`taxOf` 从低档往上找第一个「不超过上限」的区间，用 `应纳税所得额 × 税率 − 速算扣除数` 计算。

这里有一个必须讲清楚的口径问题：页面标题写的是「累计预扣」，但代码算的是**年税平均到月**。真实的工资薪金累计预扣法下，同样年薪的人，年初扣得少、年末扣得多，月度到手并不是一条直线。这个工具给出的是全年平均视角，适合估算和比较，不适合拿去和工资条逐月对账。页脚其实也承认了这一点——「平均到月」。

知道它是什么，比让它假装是另一个东西更重要。

## 反推税前：80 次二分

正算很容易，难的是「我想到手 15000，税前要多少」。工资到到手是单调的：税前越高，到手越高。于是可以直接二分。

```js
let lo = 0,
  hi = Math.max(netTarget * 3, 10000)
for (let i = 0; i < 80; i++) {
  const mid = (lo + hi) / 2
  const r = calc(mid)
  if (r.netMonthly > netTarget) hi = mid
  else lo = mid
}
return calc(Math.round(lo * 100) / 100)
```

80 次迭代远超浮点精度需要，成本可以忽略；上界取「目标到手 × 3」和 1 万元中较大的那个，避免目标很高时区间不够。每次输入触发反推时，防抖是 120ms，避免一边打字一边跑 80 次完整计算。

缺点也明显：它假设所有比例和扣除在区间内恒定，不考虑税率跳档造成的非连续一阶导，也不处理年终奖。作为估算够用，作为报税工具不够。

## 年终奖：两套算法，取更优的那个

年终奖有两种常见口径：单独计税，和并入当年综合所得。代码两种都算：

- **单独计税**：奖金除以 12 去查按月换算税率表，再用**奖金全额**乘以税率减速算扣除数；
- **并入综合所得**：把奖金加到年应纳税所得额上重算年税，差额就是奖金对应的税。

```js
const bonusSepTax = bonusTax(bonus);
const bonusMergeExtra = annualTaxMerged - annualTax;
const bonusMergeNet = bonus - bonusMergeExtra;

// 全年总到手：两种方案里取更高的那个
yearNet: netMonthly * 12 + Math.max(bonusSepNet, bonusMergeNet),
```

页面上会把两个方案的到手都列出来，全年总览则取较优者。要强调：这是**展示最优方案**，不是替你决定申报方式，也没有处理年终奖的临界点盲区（比如 36000 与 36001 元可能对应完全不同的税档）。现实中的选择还受当年其他收入、汇算清缴影响。

## 边界：静默夹紧，或者干脆不显示

这份代码对异常输入的处理很「安静」：

- 工资小于等于 0 时，结果区直接隐藏，不显示一排零；
- 负数、空值、非数字被 `num()` 吞成 0，等于没填；
- 公积金比例被 `clamp(0, 20)`，但 HTML 输入框写的是 1–15，手输可以越过界面约束；
- 其他险种比例没有上限，极端输入可以让五险超过工资；
- 下限大于上限时，结果静默变成上限；
- 内部全程浮点，逐项不取整，只有展示时保留两位小数。

这些行为在个人工具里可以接受，但它们没有提示、没有错误态，用户只能从结果反推自己填错了什么。如果要做成给别人用的产品，第一件事应该是把这些静默分支变成可见的校验。
