把一段网站浏览录屏交给 AI，让它还你一个能跑的页面——这件事最诱人的地方，是演示视频里那种「看着就自动做出来了」的流畅感。最危险的地方也一样：**看起来做出来了**。

这次我完整跑了一遍 video2code 插件（0.6.0），复刻 Raycast 首页。最终得到一个 React + TypeScript + Vite + Tailwind 的单页应用、38 项检查全部走完、验证台账终态全绿。但我后来去核了证据文件的哈希，发现「全绿」只说明清单走完了，离「像」还差一层：**被断言的东西，未必真的被证据覆盖**。

这篇写三件事：这套工作流是怎么运转的、它哪些地方做得对、以及我是怎么用哈希把一份全绿的验收记录问出破绽的。

## 一、先写计划，不写代码

插件的第一条硬规矩是：**动手写页面前，先把视频拆成可验收的条目**。

复刻对象是 Raycast 官网首页，1280×800 视口，一路向下滚完。原始录屏约 70 秒，前 20 秒是页面首屏加载的空白帧——这段被裁掉，保留 49.4 秒作为验证基准。这个裁剪不是小事：它决定了后面所有「第几秒对应哪个区块」的对齐关系，所以必须写进报告，而不是悄悄剪掉。

产出的 `out/plan.md` 里，每个视觉单元都有一个 id：

```text
[S2] Hero: full-viewport section; centered 3-line display headline ... {core}
[D1] Hero entrance: headline fades from dim/blur to full white over ~1.0s
     (source clip 0.5–2.5s; CSS animation; testid=hero-headline) {core} {render}
```

三类标记各管一件事：

- `S` 是静态项（结构、文字、颜色、字号），`D` 是动态项（淡入、跑马灯、轮播、滚动联动）；
- `{core}` / `{detail}` 是权重。核心锚点不允许「目测没差别，沿用旧图」，代码改过就必须重拍；
- `{render}` / `{footage}` 是像素来源。`{render}` 要求该区域由代码实时生成，`{footage}` 才允许直接铺源视频素材。

最后那一条很关键。复刻任务里最省事的作弊方式，就是把源录屏裁一块当背景图贴上去；页面「看起来」和源一模一样，实际上没有实现。插件为此专门有一条资产溯源规则：`app/public` 下的动态资产必须能在计划里找到对应的 `{footage}` 声明，`{render}` 项则不许带 `asset=`。

这次的页面被判定为全部 `{render}`——13 个区块、24 个 S 项、14 个 D 项，另有 7 个全帧锚点（S18–S24）。计划阶段就把「哪里必须是真的」钉死了。

## 二、14 个动效，14 个状态机

静态布局可以靠眼力和 CSS 逼近，动态效果不行。计划里每个 D 项都带源片时间段和实现机制，写代码时逐条落成状态机：

- 推荐语每 3 秒向左滑一位，当前人物高亮；
- Snippets 输入框逐字符打字，弹出自动补全，停留后清空重来；
- 页脚邮箱占位符在 `bjarne@cplusplus.com` 和 `matz@ruby-lang.jp` 之间轮换；
- 导航右侧的「Log in / Download」在滚过阈值后才淡入，回到顶部再淡出；
- 键盘说明卡随滚动逐张点亮，且可逆。

实现上没什么魔法：React 组件 + 两个共享 hook（滚动进度、进入视口），定时器负责轮换，CSS keyframes 负责跑马灯和光标闪烁。真正难的是**把每一段动效和源视频里的一段时间对上**，而不是写出动效本身。

这里出现了第一个诚实的缺口。AI Chat 演示窗在 49 秒的源片里只被拍到「已停稳」的状态（约 22.5–27 秒），完整循环根本没在画面里走完。复刻只能按 2.6 秒一步的节奏实现，机制对得上，节奏是估的。这条被写进了报告的 Known limitations——不是补丁说明，而是验收边界。

## 三、取证协议：一条判定一行 JSON

验证不是「看一眼觉得行」，而是往 `out/verify.jsonl` 追加记录。每个 id 每次判定一行，状态必须写在字面量 `result` 上，值只能是 `pass` / `fail` / `defer`：

```json
{
  "id": "D13",
  "result": "pass",
  "evidence": "out/cmp/D13_nav-threshold.png",
  "measured": { "trigger": "scroll threshold both", "state": "absent@top + present@deep both" },
  "diffs": [
    {
      "what": "REP threshold 6000 vs src ~8000 (page height differs)",
      "severity": "minor",
      "disposition": "negligible: same mechanism"
    }
  ]
}
```

`evidence` 指向 `out/cmp/` 下的 SRC|REP 成对合成图。左侧是源视频在某个时刻的帧，右侧是复刻页在对应节拍的截图，中间用分隔线隔开。下面的 hero 对比就是其中一张：

![Raycast 首页 hero：左为源视频帧，右为复刻页](/static/images/blog/202610/Video2code/01-hero-pair.png)

这一轮一共产生 67 行非空记录，其中 66 行是合法 JSON。38 个 id 全部有终态，62 条 `pass`、4 条 `fail`。四个失败都是首轮实打实的问题：

- S18：复刻页标题比源高约 200px；
- S19：Linear 卡的弧线太小、整体左偏；
- S20：AI 窗高度只有约 430px，源是 500px+；
- S22：bento 网格被 `max-w-1440` 限制，源是全宽。

修完追加新的 `pass` 行，旧行不删。台账因此保留了修复轨迹，而不是只留一个漂亮结论。

## 四、审计规则：把「验收」写成代码

插件的 Stop hook 会在会话准备收尾时跑一遍 `contract_audit.py`，不闭环就拦住。审计规则一共八条（C1–C8），核心是这些：

- **C1 覆盖率**：计划里的每个 id 都要有终态记录，且状态键必须叫 `result`；
- **C2 报告**：`out/report.md` 要真的填过，骨架标记必须删掉；
- **C3 成对证据**：D 项的 `pass` 证据必须位于 `out/cmp/` 且文件存在；
- **C4 证据归属**：证据文件名必须包含本 id，合并命名（如 `D2_D14_*.png`）合法；
- **C5/C6 新鲜度**：最后的代码编辑之后必须重新取证；核心锚点尤其不许沿用旧图；
- **C7 账面纯度**：`pass` 行的 `diffs` 里不能还留着 `disposition=fix` 的未修项；
- **C8 资产溯源**：动态素材必须对上计划里的 `{footage}` 声明，`{render}` 不能夹带源素材。

这套设计里最值得抄走的是**单点规则**：同一份审计模块同时供模型自查、Stop hook 兜底和流水线记账使用，避免「文档一套、脚本一套」。hook 还留了三个现实出口——工作区声明放弃、契约归属别的会话、同一会话被拦满三次——防止一个废弃任务把后续所有会话都卡死。

## 五、全绿之后，我核了哈希

问题就出在 C3 和 C4 的强度上。

C3 只检查路径里有没有 `/cmp/`、文件在不在；C4 只检查文件名里有没有这个 id。两条规则都**不检查文件内容，也不检查证据类型**。于是一个全帧锚点图，复制一份、改个名字，就能同时充当某个动态项的「成对证据」。

我把 38 条证据引用全部展开：21 个唯一文件，算 md5 后只剩 16 个唯一值——**有 5 组文件字节级完全相同**。

| 重复组                                            | 实际内容                                           |
| ------------------------------------------------- | -------------------------------------------------- |
| `D2_D14_reveal.png` = `D2_kbd_pair.png`           | 键盘区锚点，D2 与 D14 共用                         |
| `D7_D8_ai-section.png` = `S20_C-ai_r2.png`        | AI 区锚点，D7/D8 共用                              |
| `D9_D10_whatelse.png` = `D9_words_pair.png`       | What-else 区锚点，D9/D10 共用                      |
| `D12_footer-placeholder.png` = `S24_G-footer.png` | 页脚锚点，D12 共用                                 |
| `D11_bento-zone.png` = `S22_E-bento_r2.png`       | **bento 区锚点**，却用来证明 D11 的 YouTube 跑马灯 |

前四组还在同一区块内，共用锚点图至少能证明静态构图一致；第五组是错位：D11 要验的是 YouTube 标题条向左滚动，而证据图拍的是下方的 build bento 网格，两者根本不在一个画面里。台账里 D11 的 `reason` 写得很坦白——"merged-name copy of the bento-zone anchor covering D11"——但审计只认文件名里的 `D11`，于是照样放行。

![Raycast AI 区：左为源视频帧，右为复刻页；这张锚点同时被 D7/D8 复用](/static/images/blog/202610/Video2code/02-ai-pair.png)

还有一层：**动态项需要的是时间，不是静帧**。真正带时序的复刻侧 contact sheet 只有 6 张，覆盖 D1–D6 和 D9 共 7 个 id；其余 7 个 D 项（D7、D8、D10–D14）的 `evidence` 都是静帧。D8 的光标闪烁、D10/D11 的跑马灯方向、D12 的占位符轮换、D14 的淡入幅度，在单张图上都无法被证明。

更尴尬的是 D7 的 `reason`：它声称 "recording repD3/repD4 grids show stage progression"。我去看了这两张图——`repD3` 拍的是 hero 到扩展卡，`repD4` 拍的是扩展卡到推荐语，没有一张包含 AI 聊天窗。也就是说，这条动态项的取证说明引用错了文件，而审计不会读 `reason`。

同一份台账里还有一处小裂缝：第 23 行是一条被截断的 D12 记录（306 字符，JSON 中途断掉）。审计解析失败就跳过，不告警。这次因为后面还有一条完整的 D12 `pass`，账面没有缺口；但如果被截断的恰好是修复后的最后一次判定，审计就会继续拿更早的 `pass` 当终态——**解析失败是静默的，只有 id 缺失才会触发 C1**。

另外，报告正文写的是「60 行判定」，实际台账是 66 行合法记录。人写的摘要和机器写的账本之间，没有任何一致性检查。

## 六、所以还原度到底是多少

我没有一个可信的百分比。

这次验收里没有 SSIM、没有 DOM diff、没有 CLIP 相似度，`pass` 的含义是「模型看了某个节拍的 SRC|REP 合成图后判定一致」。7 个全帧锚点的静态构图确实对得比较齐，连标题字号、窗口高度、侧栏宽度都量了像素级估值；但动态部分有一半靠文字断言。

如果一定要给一个可复核的结论，应该是这样一串事实，而不是一个分数：

- 38 项检查全部有终态判定，4 个首轮失败都修复并复验；
- 7 个静态锚点有独立的全帧成对图；
- 14 个动态项里，7 个有时序 contact sheet；
- 5 组证据文件字节级重复，其中 1 组（D11）与所验区域不符；
- 1 条验证记录损坏后被静默跳过；
- AI 循环节奏、导航阈值（6000 vs 源约 8000）、Linear 弧线、Spotify 封面都是近似实现，已列入 Known limitations；
- **从未部署**，报告里的 "Deployed URL" 是 `http://localhost:3460`。

最后一条尤其值得单独说。一个「复刻网站」任务，如果产物只在本机 `app/dist` 里跑过，它的完成定义其实是缺角的。部署不是装饰性步骤，它会暴露静态资源路径、构建产物体积、跨域和缓存问题——这些都不在截图里。

## 七、如果重做这个插件，我会改什么

不是加更多提示词，而是**让证据格式长出牙齿**。

1. **证据结构化**。`evidence` 不该是自由文本，而应是 `{id, kind, t_src, t_rep, files: [{path, sha256}], tool}`。有了哈希，跨 id 复用一查便知；有了 `kind`，就能要求 D 项必须提交 `clip` 或 `beat_grid`，而不是一张静帧。
2. **C3 分级**。静态项接受单张成对图；动态项至少要求 3 个匹配节拍，或一段不超过 10 秒的复刻录像。只写 "mechanism matches" 不算证据。
3. **C4 加上区域约束**。合并命名可以保留，但同名证据必须声明它覆盖哪些 id、对应哪个区块；跨区块复用直接判缺口。D11 这种错误就会在收尾时被抓住。
4. **解析失败要报警**。JSONL 有坏行时，审计应输出行号和原文摘要，而不是静默跳过。
5. **报告数字由台账生成**。「60 行」和「66 行」的漂移，靠人写永远会发生；让报告引用台账统计结果，比再写一条检查规则更省事。
6. **完成定义包含部署**。至少要有一次真实静态托管上的可访问 URL，并把它写进 C2。

还有一个不那么技术的问题：一页 13 个区块、14 个动效，信息密度已经接近单轮任务的上限。Linear 弧线只能 SVG 重画近似，Spotify 封面只能用黑白人像抽象替代——这些妥协本身没问题，问题是它们被埋在 `diffs` 的 `negligible` 里。更合理的做法是按区块分段验收，每段先过静态锚点，再补动态取证，而不是最后一次性汇总。
