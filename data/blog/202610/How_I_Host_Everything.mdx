## 二、先分类，再选平台

如果重新选一次，我只问四个问题：

1. **只有静态文件吗？** 是 → GitHub Pages 或 Cloudflare Pages。两者都能托管，差别在带宽、构建和自定义域。
2. **需要函数吗？** 是 → Vercel（Node 生态、Next.js 一体）或 Cloudflare Pages Functions（更轻、更便宜，但 CPU 限制紧）。
3. **需要数据库吗？** 需要 → Neon 之类的外部 Postgres，别把状态塞进平台存储。
4. **需要定时任务，而且一天不止一次吗？** 是 → 别指望 Vercel Hobby 的 Cron；用外部调度器或 Cloudflare 的定时触发器。

这四个问题里，最容易误判的是第一题。CET4Lab 看起来是静态题库站，其实有一个 `/api/listen` 路由：源 CDN 只服务国内线路、不带 CORS 头，浏览器直接拉会失败，所以必须经同源代理，而且函数要固定在 `hkg1`，让出口能连上源站。这种「一个静态站里藏着一个必须存在的函数」的情况，会让「静态站不需要服务端」的判断失效。

反过来，Vercel 上的 Cha、GitHub Guide、GitHub Wrapped、Toolbox 都是纯静态。它们留在 Vercel 不是技术需要，只是部署顺手。**平台数量多，不等于每个平台都在发挥不可替代的作用。**

几条不那么直观的结论：

- **Vercel 的 100 万次调用很多，4 CPU-hours 很少。** 一次函数调用如果只等 I/O，CPU 时间很短；一旦做图片处理、加解密或大 JSON 解析，4 小时会比你想象得快。DeepLearn 的 AI 出题 60 秒上限看起来很宽，但那是墙钟时间，不是 CPU 时间。
- **Cloudflare 的 KV 写额度是图床的真上限。** 每天 1000 次写，不是 1000 次上传——一次上传可能写多个 key。读额度 10 万/天反而很宽。真要做大，应该换 R2 或 D1。
- **GitHub Pages 的 100 GB 是软限制，但证书是硬故障。** 额度没超，站点也可能因为证书没签发而打不开；这次 SalaryCalc 就是，当天晚些时候已补发（见文末补记）。
- **Neon 免费档不是「一直醒着」。** 5 分钟闲置就挂起，冷查询会慢一拍；6 小时恢复窗口意味着误删数据最多只能回到 6 小时内，这不是备份，是止损。
- **Vercel Hobby 只允许非商业个人用途。** 这 15 个站现在都是个人项目，没问题；哪天某个站接广告或赞助，先看条款，再谈迁移。

## 四、这次巡检发现的三个洞

我在 2026-10-21 逐个请求了 15 个域名。结果是 11 个 `200`、2 个 `307`、1 个 TLS 失败。两个 `307` 是 RSS Reader 和 Treasury 的登录跳转，不是故障——**用「只看 200」的探针会把它们误报成宕机**。

### 洞一：SalaryCalc 的证书没有签发

```text
$ curl -I https://salary.adcakeyuan.top
curl: (60) schannel: SNI or certificate check failed: SEC_E_WRONG_PRINCIPAL
```

HTTP 是通的，DNS 也正确解析到 GitHub Pages 的四个 IP。问题在 Pages 侧：

```text
$ gh api repos/huqinyuan923-hue/salarycalc/pages
{"cname":"salary.adcakeyuan.top","https_enforced":false,"status":"built"}
```

同一平台的 FileKit 和 PomoBox 都是 `https_enforced: true`，证书正常。所以不是 GitHub Pages 整体故障，而是这个站点的证书状态卡住了。常见处理顺序是：在仓库 Settings → Pages 里重新保存一次自定义域，等证书签发，再勾选 Enforce HTTPS，最后用 `curl` 和 Pages API 复核。发布后经确认，已按这个顺序修复，过程见文末补记。

### 洞二：博客的 `/stats` 反代在静态导出里根本不存在

博客的 `next.config.js` 里有一段反代：

```js
async rewrites() {
  return [{ source: '/stats/:path*', destination: 'https://analytics.umami.is/:path*' }]
}
```

它把 `/stats/script.js` 转到 Umami。但博客是 `output: 'export'` 的静态站，`rewrites()` 是服务端能力，导出后不会生成任何路由。线上实际请求：

```text
GET https://adcakeyuan.top/stats/script.js  →  404（返回的是 404 页面，约 403 KB HTML）
```

目前它没造成可观测的损失，因为 `NEXT_UMAMI_ID` 没有配置，页面根本没加载统计脚本。但这是一颗埋着的雷：哪天打开 Umami，脚本会 404，统计静默为空。静态导出还会同样丢掉 `headers()`——博客现在靠 Cloudflare 的 `public/_headers` 文件补安全响应头，而不是靠 Next 配置。**从 Vercel 迁到静态托管时，`rewrites` 和 `headers` 必须逐条翻译成平台配置，不能假设它们跟着代码走。** 发布后已删掉这段反代，Umami 组件改为直连 `analytics.umami.is`（仍未启用），日常统计看 Cloudflare Web Analytics。

### 洞三：博客在两条流水线上同时发布

博客的 GitHub Actions 里还有一个 `deploy.yml`，每次推 `main` 都会构建并部署到 GitHub Pages。这次巡检时它最近一次运行是成功的（2026-10-21 02:44，耗时 1 分 39 秒）。仓库的 Pages 设置也还挂着 `cname: adcakeyuan.top`。

但 `adcakeyuan.top` 的 DNS 指向 Cloudflare，线上响应头是 Cloudflare 的。也就是说：

- 真正对外服务的是 Cloudflare Pages；
- GitHub Pages 每次 push 也构建一份，只是域名没指过去；
- `huqinyuan923-hue.github.io` 会 301 到 `http://adcakeyuan.top/`，再由 Cloudflare 升级到 HTTPS，多一跳。

它现在不是故障，而是一份「隐形冷备」：如果 Cloudflare 挂了，把 DNS 切回 GitHub Pages 理论上能顶一会儿，但没人验证过、也没写切换步骤。更现实的问题是**每次 push 构建两遍、维护两套静态导出配置（都要执行 `mv app/api api.disabled`）**，以及「哪条是主发布线」在仓库里没有答案。要么删掉 `deploy.yml` 和 CNAME，把 Cloudflare 定为唯一发布线；要么保留它，但写成明确的灾备流程并定期演练。发布后按前一种方案处理：删除 `deploy.yml` 和 `CNAME`，推送不再触发 Pages 部署，Cloudflare 成为唯一发布线。GitHub 不允许关闭 `<user>.github.io` 仓库的 Pages，所以旧站点配置还在，但不会再更新。

真正的成本在别处：

1. **证书与域名状态**：一个站点证书卡住，就是一次线上不可用；免费平台不会主动打电话提醒你。
2. **冷启动**：Neon 5 分钟挂起、Vercel 函数冷启动，第一次请求的体验由平台决定。
3. **双线部署与配置漂移**：博客的 `_headers`、GH Actions、Cloudflare 构建三处各有一份规则，改一处不等于改三处。
4. **备份**：Neon 的 6 小时恢复窗口不是备份；数据库该定期导出，静态内容该在 git 里。
5. **注意力**：15 个站意味着 15 份依赖、15 个证书、15 条部署链。这次巡检就花了半天，而且只查了「能不能打开」，没查链接、没查 API。

所以「每月 0 美元」是一个准确的数字，但不是一个完整的成本。**免费额度买到的是资源，不是运维。**
