这个项目的起点不是「我要做一个 ChatGPT」，而是一个更小的问题：**一个语言模型的最小闭环，到底由哪些零件组成？**

我把问题拆成四件事：语料、tokenizer、Transformer、训练循环。四件都在这个项目里完成，不下载预训练权重，不调任何 API。最后再加一件：把权重搬到浏览器里，让读者打开网页就能看到它写字。

模型很小，2.23M 参数；语料也不大，316,810 个字符。它写不出完整文章，但它把「文本 → 训练 → 权重 → 推理」这条链路完整走了一遍。这篇文章记录的就是这条链路。

第一版训练完之后，它确实学会了 Markdown 和代码块的节奏——续写里全是反引号、花括号和表格残片，能看，但基本没法读。于是有了第二次训练：先把语料洗干净，再在干净语料上微调 1,200 步。

## 语料：把这个博客自己喂给模型

我没有去网上找通用语料，因为那样模型学到的是别人的文风，和这个博客没有关系。语料是从本地项目里现抽的，`extract.mjs` 做三件事：

1. 扫 `data/blog` 下全部文章，去掉 frontmatter、JSX 标签和代码围栏标记；
2. 收 cha-lang 的 README、系列大纲和示例程序；
3. 收 `C:/works` 下各项目的 README。

最后得到 **75 篇文档、316,810 个字符、2,081 个不同字符**。中文占 27.2%，剩下的主要是英文、代码和 Markdown 符号。出现频率最高的字符是空格，然后是 `e`、换行、`t`、`o`——这个分布已经很诚实地说明了语料的构成：它不是一个纯中文语料，而是一个「博客 + 代码仓库」的混合体。

这带来一个后面会反复出现的副作用：模型会把 Markdown 的星号、代码块的反引号、JSON 的花括号一起学进去。它写出来的东西经常像「博客和代码的混血」，这是语料决定的，不是模型突然有了个性。

### 返工：把代码从语料里洗掉

第一版生成的样本里，代码块、表格分隔线、URL 残片占了很大比例。统计了一下原始语料：围栏代码块 30.8%、URL 9.7%、表格 6.9%、图片语法 5.7%，真正的散文不到一半。2.2M 参数的容量，有相当一部分花在了学 Markdown 语法上。

于是写了第二个抽取脚本 `extract_prose.mjs`：

- 去掉 frontmatter、围栏代码块、表格、图片、URL、JSX，以及博客模板尾部（`Back to posts`、目录、`Edit on GitHub`）；
- **保留**行内代码的文本，只去掉反引号——否则「结构有 `BrowserRouter` 和 `HashRouter` 两种模式」会变成「结构有 和 两种模式」这种缺词的句子；
- 丢掉纯英文代码行，但含中文的行一律保留，避免把代码注释里的中文说明误杀。

清洗后得到 **72 篇文档、133,072 个字符**，中文占 54.1%，代码块为零。微调沿用第一阶段的 2,081 字符表，其中有 44 个新字符（后来文章里的 emoji）不在表里，直接跳过。语料小了一半多，但每个字符更像「人话」。

## 字符级 tokenizer：2,081 个 token 的极简方案

我没有训练 BPE，也没有用现成的 tokenizer。做法简单到只有三行：

```python
corpus = open('corpus.txt', encoding='utf-8').read()
chars = sorted(set(corpus))
stoi = {c: i for i, c in enumerate(chars)}
```

**每个字符就是一个 token**。中文不需要分词，「字节码」是 3 个 token；代码里的 `{`、`}`、`*` 也各自是一个 token。这样做的好处是没有 tokenizer 的训练和对齐问题，所有字符一视同仁；坏处是同样一段话占的 token 更多，每个 token 承载的语义也更少。

对 2M 参数的小模型来说，这个取舍是合适的：它把「分词」这个变量彻底消掉了，模型学不好就只能是模型本身的问题，不会甩锅给 tokenizer。

## 模型：2.23M 参数，够小才跑得动

架构是标准的 decoder-only Transformer，配置如下：

| 项目     | 值                              |
| -------- | ------------------------------- |
| 层数     | 4                               |
| 注意力头 | 4                               |
| 隐藏维度 | 192                             |
| 上下文   | 256 个字符                      |
| 词表     | 2,081                           |
| 参数量   | 2,228,544                       |
| 权重绑定 | 输入 embedding 与输出 head 共享 |
| Dropout  | 0.15                            |

每个 block 是 Pre-LN 的因果自注意力 + GELU MLP：

```python
mask = torch.triu(torch.ones(T, T, dtype=torch.bool), 1)
h = self.ln1(x)
a, _ = self.attn(h, h, h, attn_mask=mask, need_weights=False)
x = x + a
x = x + self.mlp(self.ln2(x))
```

输入 embedding 和输出 head 共享同一份权重，这是从 nanoGPT 学来的做法：既省参数，也让输入和输出在同一个向量空间里。2,228,544 个参数，用 int8 存大约 2.2MB——比一张手机照片还小。

## 训练：CPU 上的 2,500 步

机器没有独立 GPU，全程 CPU 训练（PyTorch 2.14.1+cpu，24 线程）。超参也很朴素：

- batch 16，上下文 256，每步 4,096 个 token；
- AdamW，学习率 3e-3，100 步 warmup 后余弦衰减；
- dropout 0.15，梯度裁剪 1.0；
- 训练 2,500 步，大约 1,024 万个 token，相当于在 30 万字符的训练集上过 34 遍左右。

每 100 步在验证集上算一次 loss，只有验证 loss 创新低时才保存 `ckpt.pt`。最后 best val 是 **3.235**（发生在第 2,500 步），最终 train loss 约 **2.224**，训练循环耗时 **37.0 分钟**。

作为参照：词表是 2,081，随机猜的交叉熵是 ln(2081) ≈ 7.64。best val 3.235 意味着模型对下一个字符已经有了一定的把握，但离「会写文章」还很远。

### 第二阶段：在散文语料上微调 1,200 步

先说一个试错：我最初在清洗后的散文语料上**从零**训了 3,000 步，验证集却停在 4.22，比第一版模型在同一份散文验证集上的 3.80 还差。133K 字符对 2.2M 参数来说太少了，语料变干净，但信息量也少了一半多。于是改成微调：以第一阶段的 ckpt 为初始化，沿用 2,081 词表，只换数据。

超参也相应收小：学习率 5e-4，warmup 50 步，余弦衰减，batch 16，dropout 0.1，训练 1,200 步。散文验证集上的 loss：

|  step |   val |
| ----: | ----: |
|   200 | 3.734 |
|   400 | 3.757 |
|   600 | 3.829 |
|   800 | 3.765 |
| 1,000 | 3.760 |
| 1,200 | 3.755 |

最低点是第 300 步的 **3.713**，之后略有回升——1,200 步时训练 loss 已经降到 2.6，验证 loss 却下不去，是教科书式的过拟合。这里的 3.713 和第一阶段的 3.235 不能直接比：验证集换了，散文这份更难预测。

但**上线用的是第 1,200 步的权重**，不是最低点那份。理由是可读性指标：同一份评测脚本、同一组固定种子，1,200 步版本的输出中文占比更高、代码符号更少（后文「采样层」一节的消融表第 2、3 行）。两份权重的验证 loss 只差 0.04，而 demo 是给人看的，我按输出选。这个决定不算对——如果有人要拿权重继续训练，应该拿 3.713 那份。

## int8：把模型压到 2.2MB

训练完的 `ckpt.pt` 是 fp32，约 8.9MB。导出时我对每个二维权重矩阵做了**按行对称量化**：

```python
amax = np.abs(w).max(axis=1)
scale = np.where(amax > 0, amax / 127, 1.0).astype(np.float32)
q = np.rint(w / scale[:, None]).clip(-127, 127).astype(np.int8)
```

每个输出行有自己的 scale，`w ≈ q * scale`。LayerNorm 的权重、bias 这些一维小张量保留 fp32，因为它们占比很小，量化收益不大。最终 int8 权重 **2,218,176 字节**，加上元数据和 scale，整个二进制约 **2.2MB**。

量化对精度的影响（散文验证集）：

| 版本 | 验证 loss |
| ---- | --------- |
| fp32 | 3.7568    |
| int8 | 3.7593    |

（训练日志里的 best val 用随机窗口估计；这里的 fp32 / int8 是导出脚本在固定的 24 个验证窗口上复测的，绝对值不能逐位对比。）

差了 0.0025。对这样一个本来就不追求精度的模型来说，这个代价可以忽略。**int8 只是省空间和带宽，它不会让模型变聪明。**

## 浏览器里手写一次前向

页面没有用 ONNX Runtime，也没有用 WebGPU：2.2M 参数太小了，手写循环足够快，还能少一个依赖。

核心是一个 int8 点积：

```js
for (let o = 0; o < rows; o++) {
  let s = 0
  for (let i = 0; i < cols; i++) s += q[o * cols + i] * x[i]
  out[o] = s * scale[o] + bias[o]
}
```

生成时用了 KV cache：每个新字符只算自己的 q/k/v，然后和缓存里的历史 k/v 做注意力，而不是把整个前缀重新跑一遍。否则生成 160 个字符的计算量会翻几十倍。

```js
const cacheBase = (layer * nHeads + head) * block * headDim
kCache[cacheBase + pos * headDim + d] = k[d]
```

实现完之后我做了两次数值对齐：同一段 prompt，PyTorch 和 JS 的最后一位 logits 最大误差 **1e-5**；用贪心解码连续走 24 步，**24/24** 个 token 一致。这个误差来自浮点累加顺序和 GELU 的 erf 近似，已经足够小。

页面跑在 Web Worker 里，权重通过 fetch 流式加载，生成时逐字 postMessage 回主线程，所以主线程不会卡。这台机器上的 Chromium 实测：空闲时约 **110 tok/s**（160 字 1.4 秒），机器上同时跑着别的东西时会掉到 **73 tok/s**（160 字 2.2 秒）——同一个页面、同一份权重，差距全在 CPU 争用上。手机和低功耗设备会慢一些。

## 采样层：把乱码挡在输出之前

换权重只解决了一半问题。另一半在 `sample()` 里——第一版页面只有最朴素的 top-k 采样，小模型的所有坏毛病都被原样放大。这一轮改了四处：

**1. 修了一个 tokenizer 的 bug。** 提示词里遇到词表外的字符（emoji、生僻字）时，旧代码用 `stoi.get(c) ?? 0` 兜底，而 id 0 恰好是换行符。也就是说，你输入一个 emoji，模型就在提示词里凭空看到几个换行，后面的分布整个跑偏。现在词表外字符直接丢掉：

```js
encode(text) {
  const ids = [];
  for (const c of text) {
    const id = this.stoi.get(c);
    if (id !== undefined) ids.push(id);
  }
  return ids;
}
```

**2. 重复惩罚。** 最近 96 个 token 的 logit 除以 1.15（负的乘 1.15，保持符号），这是最常见的做法，压掉「慢慢慢慢」这种原地打转。

**3. 禁止复读 n-gram。** 比重复惩罚更狠：如果当前结尾的 3 个字符在历史上出现过，就把当时紧跟其后的那个 token 的 logit 设成 `-Infinity`。它防的是「整句整句地抄自己」——惩罚只是削弱，这个是直接封杀。

**4. 干净模式。** 页面默认勾选的一栏，做两件事：把一批符号的 logit 置 `-Infinity`；连续拉丁字母到 3 个就禁掉字母表，逼它别再用 `tionrexl` 假装英文。

这一条上线后又返了一次工。第一版只禁了 21 个 Markdown / 代码符号，我在真实浏览器里复验时看到输出长这样：`ref 的 inp-sta、代码`、`3.2 out()`、`map：Cl+cal`。括号、点号、加号、连字符、半角冒号全都漏了。中文散文用的是全角标点（，。：；？！（）），ASCII 标点小模型吐出来基本只会是代码残片，所以第二版把它们一并禁掉，只留汉字、字母、数字、空格和换行：

```js
// v1：21 个 Markdown / 代码符号
const BAN_V1 = '#*_`{}[]<>|\\=;~^$@"\'/'
// v2：补上 ASCII 标点，中文散文不需要它们
const BAN_CHARS = BAN_V1 + '.,:!?()+-&%'

function applyCleanMask(logits, history) {
  for (const id of banIds) logits[id] = -Infinity
  if (history.length >= 3) {
    const tail = history
      .slice(-3)
      .map((id) => model.decode(id))
      .join('')
    if (/^[A-Za-z]{3}$/.test(tail)) for (const id of letterIds) logits[id] = -Infinity
  }
}
```

## 它不会做什么

必须把话说清楚：这是一个**教学模型**，不是产品。

- 它不会回答问题，也没有指令微调。你给它「帮我写个周报」，它只会顺着字符概率往下编；
- 上下文只有 256 个字符，写不了长文；
- 第一版语料里中文只占 27.2%，其余大量是代码和 Markdown；微调语料中文提到 54.1%，但只有 13.3 万字符，覆盖面很窄；
- 它可能复述训练语料里的句子。2M 参数记不住整篇文章，但记住局部片段是可能的；
- 散文验证集上 3.755 的 loss 仍然不低（随机猜是 ln(2081) ≈ 7.64），错误是常态；
- 关掉干净模式，输出立刻退回代码残片和 Markdown 骨架。

如果你需要一个能完成任务的模型，去用 API；如果你想亲眼看看 LLM 内部的矩阵乘、注意力和采样长什么样，这个 demo 的前向代码全部在浏览器里，可以直接读。
